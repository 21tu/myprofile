# note 記事の作成手順

note 記事を企画から公開まで進めるための手順。素材とルールは次のファイルを参照する。

| ファイル | 用途 |
|---|---|
| `note/publishing-kit.md` | 想定読者、連載の構成、画像ルール、公開前チェック |
| `note/development-log-template.md` | 記事のもとになる開発ログ |
| `note/article-draft.md` | 第1回の下書き |
| `note/images/` | 記事で使う画像 |

役割分担: Claude Code が下書き・事実確認・記事のレビューを担当し、人間（オーナー）が内容の確定、note への投稿、公開を行う。

---

## 1. 企画する
1. `note/publishing-kit.md` の「記事の切り分け」から、書く回を選ぶ。
2. GitHub Issue を作る（`.github/ISSUE_TEMPLATE/task.yml`）。
   - タイトル例: `docs(note): 第2回 Next.js × Cloudflare の構成`
   - 「対応仕様」には `DOC-001` と、記事が扱う仕様ID（例: `FR-010`）を書く。
   - 受け入れ条件には、使う画像と、記事で「実装済み」「検証済み」と書く予定の事項を挙げる。
3. ブランチを切る: `docs/<Issue番号>-note-<topic>`

## 2. 事実を集める
記事は実際に起きたことだけで書く。執筆前に次を集める。

1. 対象期間の Issue・PR・コミットSHA
2. `reviews/` のレビュー記録と、`docs/traceability.md` の状態
3. 実行したコマンドとその結果（テスト、ビルド、Lighthouse など。測定条件も）
4. `docs/architecture-decisions.md` の関連 ADR

集めた内容は `note/development-log-template.md` を複製した `note/logs/YYYY-MM-DD_<topic>.md` にまとめる。各項目を次の3つのどれかに分類する。

| 区分 | 記事での書き方 | 根拠 |
|---|---|---|
| 予定 | 「〜する予定」「〜を目指す」 | 仕様書・ADR |
| 実装済み | 「〜を実装した」 | マージ済みPR・コミット |
| 検証済み | 「〜を確認した（条件: …）」 | 実行ログ・レビュー記録 |

根拠が見つからない事項は「予定」として扱うか、記事に書かない。

## 3. 下書きを書く
- ファイル: `note/article-<回>-<slug>.md`（例: `note/article-02-architecture.md`）。第1回は既存の `note/article-draft.md` を使う。
- 冒頭に引用ブロックで、記事の状態を書く（例: 「設計フェーズ」「第2回時点で実装済みの範囲」）。
- 構成の目安: 導入（課題・動機）→ 判断と理由 → 実際にやったこと → 結果と課題 → 次回予告
- 書かないもの:
  - 顧客名、個人の連絡先、シークレット、内部URL、本番の設定値
  - 実在しない経歴・実績・数値
  - 「WCAG 準拠」「安全」など、検証していない適合や品質の主張
- タイトル案は `note/publishing-kit.md` の「タイトル案」に追記する。

## 4. 画像を用意する
**各記事に、本文に関係する画像を最低1枚入れる。** 足りない場合は記事を完成扱いにせず、画像の作成・取得を Issue にする。

1. 画像は `note/images/<回>-<内容>.png` に保存する（既存の2点は第1回用）。
2. 記事には Markdown で相対パスを書き、alt と図番号付きの説明文を付ける。

   ```markdown
   ![モバイル版Heroのスクリーンショット。肩書き、提供サービス、問い合わせボタンが縦に並ぶ](./images/02-mobile-hero.png)

   *図1：実装済みのモバイル版Hero（commit abc1234、iPhone 15 実機で撮影）*
   ```

3. 画像の種類を説明文で区別する。
   - AI生成のデザイン案 →「デザインコンセプト」と書き、実装画面ではないと明記する
   - 実装画面のスクリーンショット → 対象のコミットと撮影環境を書く
   - 図表（アーキテクチャ図など）→ 実際に動いている構成だけを描く
4. 個人情報・秘密情報・ブラウザのタブやURLバーなどが写っていないか確認する。
5. 第三者の素材を使う場合は、利用規約と著作権を確認する。きつねのマスコットは改変・再生成しない。

## 5. 事実確認する
`note/publishing-kit.md` の「公開前の事実確認」に加えて、次を確認する。

- [ ] 「実装済み」「検証済み」と書いた文すべてに、手順2の根拠（PR・コミット・ログ）がある
- [ ] 数値（スコア、時間、件数）に測定条件と測定日が付いている
- [ ] 使ったと書いたツールを実際に使っている（接続方法も事実どおり）
- [ ] AI生成画像と実装画面を混同する表現がない
- [ ] 秘密情報・個人情報・内部URLがない

## 6. レビューを受ける
1. 下書き・画像・開発ログをコミットし、Draft PR を作る（`.github/pull_request_template.md`）。
   - 本文に `Closes #<Issue番号>` を書く。
   - 「Screenshots」欄に使う画像を載せる。
2. Claude Code が記事をレビューする。観点は事実との一致、誇張、秘密情報、画像ルール。
   - 指摘は `docs/review-policy.md` の書式（BLOCKER / MAJOR / MINOR）で残す。
   - 根拠のない主張や秘密情報の露出は BLOCKER として扱う。
3. 指摘を直し、再レビューを受ける。
4. オーナーが内容を確定し、PR をマージする。

## 7. note に投稿する（人間が行う）
リポジトリの Markdown は原稿であり、note に公開されたことを意味しない。

1. note の編集画面で新しい記事を作り、本文を貼り付ける。
   - 見出し・太字・リスト・引用・コードブロックが正しく変換されたか、プレビューで確認する。
   - 表は note でそのまま再現できないことがあるため、箇条書きか画像に置き換える。
2. 画像は **note の編集画面からアップロード** する（Markdown の相対パスは note では表示されない）。
   - アップロード後、説明文（キャプション）を記事と同じ内容で付ける。
   - 見出し画像（アイキャッチ）を設定する。本文中の画像とは別に必要。
   - トリミングで重要な部分が切れていないか確認する。
3. `note/publishing-kit.md` の「推奨タグ」からハッシュタグを付ける。
4. プレビューをスマートフォン表示でも確認する。
5. 公開範囲と公開日時を決めて公開する。

## 8. 公開後に記録する
1. 公開URLと公開日を、Issue のコメントと `note/publishing-kit.md` の「掲載素材のチェックリスト」に記録する。
2. 公開後に誤りが見つかった場合は、note 側を修正し、リポジトリの原稿も同じ内容に直す。
3. 次回の記事の材料（残った課題、次に書くこと）を開発ログに追記する。
